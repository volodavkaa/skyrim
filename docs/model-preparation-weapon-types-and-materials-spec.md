# ТЗ: типи зброї та матеріали підготовлених моделей Skyrim SE/AE

Статус: робоче ТЗ, оновлено 26.10.2026. Доповнює `model-preparation-technical-spec.md` за пунктами 2 і 3 подальшого плану. Ручна перевірка у Skyrim відкладена користувачем; автоматичний експорт не означає підтверджену роботу в грі.

## 1. Типи статичної зброї

Підтримувані кандидати: кинджал, одноручний меч, дворучний меч, одноручна сокира, дворучна сокира, булава, бойовий молот. Луки, арбалети, анімовані та skinned моделі залишаються окремими маршрутами.

|---|---|---|---|
| Кинджал | `meshes/weapons/iron/irondagger.nif` | `meshes/weapons/iron/1stpersonirondagger.nif` | За наявності придатного `Scb` у шаблоні |
| Одноручний меч | `meshes/weapons/iron/longsword.nif` | `meshes/weapons/iron/1stpersonlongsword.nif` | За вибором користувача |
| Дворучний меч | `meshes/weapons/steel/steelgreatsword.nif` | `meshes/weapons/steel/1stpersonsteelgreatsword.nif` | За наявності придатного `Scb` у шаблоні |
| Одноручна сокира | `meshes/weapons/iron/waraxe.nif` | `meshes/weapons/iron/1stpersonwaraxe.nif` | Лише якщо шаблон і правило форми це підтримують |

| Бойовий молот | `meshes/weapons/iron/warhammer.nif` | `meshes/weapons/iron/1stpersonwarhammer.nif` | Лише якщо шаблон і правило форми це підтримують |

Шляхи вище знайдено в установлених ванільних BSA, але саму придатність вузлів кожного шаблону треба перевіряти. Каталог типів зберігає шляхи, очікувані частини (видима зброя, шари крові, колізія, опціональні піхви), допустимі режими та статус. Наявність NIF у BSA сама по собі не вмикає тип для експорту.

Для кожного типу:

1. Імпортувати обидва шаблони й описати реальне дерево вузлів, матеріалів, колізії та обмеження.
2. Визначити вісь від хвата до робочої частини, орієнтир масштабу, зони крові й геометрію колізії. Вістря меча, лезо сокири та ударна голова булави/молота не мають одного універсального правила.
3. Підганяти `BloodEffects`/`BloodLighting` лише до робочої частини відповідного типу; перевіряти після повторного імпорту, що шари не накривають руків'я, мають UV та не гублять матеріал.
4. Піхви показувати як вибір тільки там, де вони конструктивно доречні й експортер може їх створити. Відмова від піхов прибирає вузол без пошкодження інших частин.
5. Перераховувати колізію на основі частин шаблону; зберігати Havok-властивості; звіряти кількість вузлів, їхні межі та матеріали після експорту.
6. Показувати тип, обидва зразки та статус перевірки в інтерфейсі. До ручного тесту в грі нові типи мають явний експериментальний статус.

Критерій приймання типу: два окремі SE NIF, повторний імпорт, видима геометрія, шари крові на робочій частині, придатна структура колізії, коректний вибір піхов і проба в Skyrim для першої та третьої особи. Якщо шаблон не має потрібного вузла, тип або відповідна опція не вмикається, а звіт пояснює причину.

## 2. Матеріали й текстури

На початку цього етапу експортер брав матеріал зброї з ванільного шаблону й не використовував PNG з ZIP. Тепер режим BaseColor/Normal створює **окремий** ресурсний комплект, не змінюючи ZIP, BSA чи файли гри.

### Джерела й відповідність

- Показати матеріальні слоти вибраної mesh і знайдені зображення архіву. Користувач явно призначає для кожного слота diffuse/base color, normal map та, за потреби, Skyrim-compatible mask/specular. Якщо є кілька кандидатів, автоматичне вгадування лише пропонує відповідність; неоднозначність блокує публікацію.
- Металевість/roughness із PBR не записувати безпосередньо в невідповідні слоти Skyrim. Для них потрібне окреме перевірене правило конверсії або чітке повідомлення, що канал пропущено.
- Зберігати UV і призначення полігонів до матеріальних слотів. Якщо UV немає або їхня структура не підтримується, показати помилку перед експортом.
- Шари крові та піхви мають власні матеріали; зміна матеріалу клинка не повинна їх перезаписувати.

### Перетворення й вихід

- Конвертер створює сумісні 2D DDS з mip-рівнями й правильним кольоровим простором: base color — sRGB, normal/masks — linear. Формат BC визначається перевіреним конвертером; альфа й normal-кодування перевіряються окремо.
- Створені DDS зберігаються в `textures/<назва-моделі>/`; NIF посилаються лише на ці відносні шляхи. Жоден абсолютний шлях із комп'ютера або шлях у тимчасовій папці не потрапляє до NIF.
- Перед публікацією перевірити DDS-заголовки, розміри, mip-рівні, хеші, усі текстурні посилання в обох NIF та відсутність невирішених залежностей. Звіт розрізняє «геометрія перевірена», «ресурси перевірені» та «вигляд у грі не перевірений».
- Режим без конверсії може залишити ванільний матеріал лише як явно обраний експериментальний варіант. Не називати такий результат текстурованою моделлю користувача.

### Безпека й відкат

ZIP розпаковується в обмежену проміжну папку з перевіркою шляхів, дублікатів, symlink, кількості й розмірів файлів. Конвертер працює з тайм-аутом і скасуванням. NIF та DDS публікуються разом після повної перевірки; помилка або відмова від чернетки прибирає весь проміжний комплект.

Критерій приймання матеріалів: на контрольній рапірі з `Rapier_BaseColor.png`, `Rapier_Normal.png`, `Rapier_Metallic.png` створено DDS diffuse/normal із коректними NIF-посиланнями для обох видів; metallic має задокументоване рішення, а не мовчазне некоректне призначення. Повторний імпорт NIF і read-only DDS-інспектор підтверджують структуру; остаточний вигляд перевіряється в грі окремо.

## 3. Порядок робіт

1. Каталог ванільних зразків і структурний аудит семи типів; UI-вибір типу без хибного статусу готовності.
2. Типові правила крові, піхов і колізії; автоматичний експорт/повторний імпорт для кожного типу на погодженому тестовому зразку.
3. Аудит матеріалів FBX/ZIP і дослідний DDS-конвертер на рапірі; явне призначення каналів, відносні NIF-посилання та атомарна публікація.
4. Автоматичні тести, перевірка у 3D-перегляді, далі відкладене ручне приймання в Skyrim перед позначенням типу чи матеріального режиму як перевіреного.

## Стан реалізації на 25.10.2026

- Каталог містить сім перевірених пар ванільних NIF. У вікні експорту доступні всі сім статичних типів із таблиці вище. Для сокир, булави та молота додано окремі правила робочої поверхні крові, хвата й колізії.
- Кинджал пройшов автоматичний цикл ZIP → FBX → два NIF → повторний імпорт для варіантів із піхвами та без них. Одноручний меч повторно пройшов той самий цикл без піхов. Форма крові копіює поверхню вихідної моделі після підгонки; початок піхов береться з фактичної межі цієї поверхні.
- Одноручна й дворучна сокири, булава та бойовий молот пройшли той самий цикл на тимчасових FBX, отриманих із їхніх локальних ванільних NIF. Одноручна сокира пройшла також тест дзеркального леза й вибору піхов. Для булави шар крові обмежується головою до верхнього шипа; для іншої ударної зброї потрібна ширша за руків’я голова. Невідповідна за формою рапіра для булави відхиляється без залишення чернетки.
- Для сокир, булави й молота межа робочої голови визначається поперечними перерізами підготовленої моделі, а не фіксованою координатою ванільного NIF. На локальних пробних зразках знайдено діапазони 11,4–33,7 для одноручної сокири та 22,4–32,7 для булави. Для одноручної сокири визначається також бік леза; її `Scb` масштабується до нової моделі й дзеркалиться за потреби. Це автоматична геометрична перевірка; ігровий вигляд піхов ще не підтверджено.
- Поверхня крові тепер геометрично розрізається на межі леза або голови; полігони, які перетинають межу, не викидаються цілком. Після цієї зміни всі сім типів повторно пройшли цикл експорту й повторного імпорту.
- Колізійні бокси тепер створюються в порядку граней, який очікує PyNifly. Інакше його експорт повертав поперечні осі бокса та автоматична перевірка справедливо відхиляла NIF.
- Для вхідного ZIP запускається аудит UV, матеріальних слотів і зображень. Звіт `source-materials.json` входить у чернетку/комплект. Для пробного Rapier FBX знайдено UV, один матеріал та BaseColor, Normal і Metallic PNG; посилань на ці зображення у вузлах матеріалу FBX немає.
- На той момент наступним етапом пункту 3 був вибір явного зіставлення джерельних зображень, конвертація diffuse/normal у DDS з mipmaps, запис шляхів у шейдерні вузли обох NIF та зворотна перевірка. Режим BaseColor/Normal виконано; Metallic і далі потребує окремого правила, його не можна автоматично вважати готовим слотом Skyrim.
- Перевірка в самій грі відкладена на прохання користувача. Пройдені перевірки підтверджують структуру NIF, а не вигляд, анімацію чи фізику у Skyrim.
### Продовження: робочий маршрут DDS

У вікні додано явний вибір BaseColor/Diffuse і Normal із ZIP, шлях до `texconv.exe` та перемикач інверсії зеленого каналу normal map. Кнопка пошуку підставляє файли лише за однозначного збігу назв; вибір можна змінити. Metallic не прив'язується до шейдера автоматично.

Під час експорту `texconv` створює `BC7_UNORM_SRGB` для diffuse і `BC7_UNORM` для normal, з повним набором mip-рівнів. Файли потрапляють до `textures/<model>/`, а матеріал зброї в обох NIF посилається на них. Формат, колірний простір, mip-рівні та посилання у NIF перевіряються до публікації чернетки. На тестовому Rapier ZIP пробний цикл успішно пройшов для одноручного меча, кинджала і дворучного меча. Для цього режиму потрібні UV; від двох до восьми матеріальних слотів вимагають явних BaseColor і Normal для кожного. OBJ без матеріального слота теж приймається: шейдер береться з ванільного шаблону, а BaseColor і Normal користувач явно вибирає з ZIP.

Офіційний інструмент конвертації: https://github.com/microsoft/DirectXTex/wiki/Texconv . Встановлення `texconv.exe` є окремим кроком; пробний файл завантажено лише до тимчасової папки. Ігровий вигляд DDS та орієнтація normal map залишаються неперевіреними до тесту Skyrim.

## Наступний етап після 26.10.2026

1. **Кілька матеріальних слотів.** Спершу перевірити на двоматеріальній пробній моделі, що PyNifly зберігає кілька окремих форм NIF з їхніми шейдерами під одним коренем. Розділити полігони зброї за матеріальними індексами, зберігши UV та положення кожної частини. Кров, піхви та колізію будувати за об'єднаною геометрією, а не за одним із матеріалів.
2. **Призначення текстур.** У вікні показувати кожен матеріальний слот і для кожного окремо вибирати BaseColor/Normal. Конвертувати зображення в окремі DDS, призначати відповідному шейдеру й перевіряти після повторного імпорту, що всі форми та шляхи збережені. Неповне або неоднозначне призначення має дати чітку помилку до публікації.
3. **Різнорідні авторські моделі.** Перевірити FBX, OBJ і GLB різних пропорцій на всіх семи типах, особливо визначення робочої частини крові й придатність піхов. Модель, для якої алгоритм не може надійно визначити зону крові чи зробити піхви, повинна отримати пояснену відмову або доступний вибір «без піхов».
4. **Інші формати й канали.** Додати залежності `.gltf`, зовнішній `.mtl` для OBJ, готові NIF та `.blend` після імпорту й перевірки. Metallic/roughness і маски потребують перевіреного правила перетворення; автоматичне копіювання в невідповідний слот Skyrim заборонене.
5. **Ручне приймання в Skyrim.** Після згоди користувача перевірити обидва види, положення в руці, шейдер крові, піхви та колізію. До цього жоден тип або матеріальний режим не позначати як підтверджений у грі.

Пункти 1–2 реалізовано на структурному рівні й перевірено на тимчасових двоматеріальних FBX меча та булави. Кожен слот має окрему форму й пару DDS; повторний імпорт перевіряє UV і прив'язку текстур по формі. Для пункту 3 також перевірено авторський FBX меча з окремою mesh піхов і довгою віссю X: два режими піхов створили по два NIF. Джерельні піхви замінюються новою підігнаною формою; збереження власної mesh піхов лишається окремою задачею. Подальші різнорідні моделі й тест у грі ще потрібні; останній відкладено користувачем.

Зовнішній `.bin` для glTF і матеріальний файл `.mtl` для OBJ тепер читаються з ZIP через обмежений тимчасовий каталог. Пробний glTF пройшов два NIF; двоматеріальний OBJ/MTL пройшов окремі DDS і повторний імпорт. Залежності за межами ZIP та відсутні файли відхиляються. MTL використовується тільки для назв і призначення матеріалів, без автоматичного завантаження текстурних шляхів із нього. Далі залишаються ширші авторські зразки цих форматів і правила для PBR-каналів.

Готові Skyrim LE NIF `Wallace Collection A474`, `DarkSister_HD` і `Fang of Namira` та пробна Skyrim SE NIF тепер пройшли автоматичний цикл. Для ZIP із кількома моделями є явний вибір файла. Кілька частин однієї зброї зберігаються як окремі матеріальні форми після підгонки. Пробні `.blend` з одним і двома матеріалами також пройшли цикл із вимкненим виконанням скриптів. Для статичної mesh підтримуються `Mirror`, `Array`, `Bevel`, `Solidify`, `Subdivision Surface`, `Triangulate`, `Weld`, `Weighted Normal` і `Decimate`: їхню обчислену форму використовують для крові, піхов і NIF; матеріальні індекси зберігаються. Непідтримувані модифікатори та shape keys відхиляються. Залишається ширша перевірка авторських NIF і BLEND, особливо їхніх піхов та нетипових дерев вузлів; PBR-канали ще не опрацьовані.
